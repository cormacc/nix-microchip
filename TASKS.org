#+IMPORT: [[plan:2026-11-26-mplab-cli-cmake.org]]
Microchip recommends that users move from MPLAB-X to MPLAB for VS Code. For CI and devshell builds, the replacement for the MPLAB-X command-line subset is the Node.js MPLAB CLI (npm =@mplab/cli=, alpha), not the VS Code extensions. The VS Code extension pack page names this CLI for CI and says that it does not need VS Code.

Package the CLI as =mplab-cli=, generate and commit CMake files for =examples/mplab/firmware.X=, and build them in a Nix derivation with =xc-cli=, =cmake= and =ninja=. The MPLAB-X path stays. CLI 0.9.6 emits a debug build only, so release hex files still come from the MPLAB-X path. The change-record holds the scope, the acceptance criteria, the decisions and the 2026-11-25 evaluation results.

The CMake path of the MPLAB CLI task builds a debug image only: =@mplab/cli= 0.9.6 passes the constant build type =debug= at both of its CMake call sites (=dist/main.js=: =const t="debug"= in =project build=, and =buildType:"debug"=), so the generated rules have =-D__DEBUG= and =--defsym=__MPLAB_DEBUG=1=. The CMake generator library inside the CLI has a =production= build type (output in a =production= folder, file name suffix =-production=), but no command-line option selects it. When a CLI release adds a production build, generate the production CMake files for =examples/mplab/firmware.X=, build them in the Nix derivation, and compare the hex with the hex of the MPLAB-X path. Check =https://www.npmjs.com/package/@mplab/cli= and the package =CHANGELOG.md= for the release. Alternative without a new release, not tested: patch the build type in the pinned package.

** TODO Make mdb run in the Nix build sandbox without extra setup

In a Nix derivation, =mdb= (=xc-cli= =withMdb=, =xc-dsc_4_00=) exits 1: MDB cannot create =/build/.mchp_packs= ("Read-only file system"), although the wrapper gives it a temporary =HOME=. Java takes =user.home= from the passwd entry of the build user (=/build=), not from =HOME=. With =HOME= set to a writable folder and =JAVA_TOOL_OPTIONS="-Duser.home=$HOME"=, the same derivation passes (measured 2026-11-26, =.tmp/mdbprobe/=). The 2026-11-25 MDB task recorded a passing derivation test, but did not rerun it after the =Simulator_TP= change. README.org "MDB" documents the workaround. Possible fix: the =mdb= wrapper in =pkgs/mplab-x/mdb.nix= passes =-Duser.home= of its temporary home to Java. Acceptance: the README MDB derivation passes without the =HOME= and =JAVA_TOOL_OPTIONS= lines, and the README drops the workaround.
