* Intent
A project runs the XC compilers that it selects, with the device packs that it selects, in a small environment without the IDE, for user Makefiles, CMake and Nix derivations. Each installation states its compilers and packs once, in `xc-cli`, and `mplab-x` uses that selection: neither has a default compiler or a default pack set.

* Summary
*Level:* production · *Tests:* smoke · *Docs:* README

** Scope
*** In scope
- `xc-cli`: root filesystem with glibc (64-bit and 32-bit), 32-bit libstdc++ and libgcc, the selected compilers at /opt/microchip/<pname>/v<version> and the selected packs at /opt/microchip/mplabx/v<version>/packs; commands `xc-run`, `xc-make` and a wrapper for each executable of the first compiler of each pname.
- `xc-cli` exposes its inputs in `passthru` (compilers, packs, FHS libraries, IDE version). A root filesystem builder and `run.sh` are shared by `mplab-x` and `xc-cli`.
- `mplab-x` takes an `xc-cli` argument and builds its root filesystem from those inputs plus the GUI libraries and the IDE. Its `packs` argument adds IDE-only packs (e.g. tool packs). It has no compiler wrappers; `mplab_ide`, `mplab-x-run` and `mplab-make` stay.
- BREAKING: `mplab-x` has no `compilers` argument, and its default `xc-cli` has no compilers and no packs; `mplab-xc8`, `mplab-xc16`, `mplab-xc32` and `mplab-xc-dsc` are removed.
- All bundled packs stay available as `mplab-x-unwrapped.packs`; `fetchMplabPack` selects single packs.
- README.org: `xc-cli` usage, the changed `mplab-x` defaults, migration from `mplab-xc*`, and the udev/licence sections that name `mplab-x-run`. AGENTS.md: the layout section.
*** Out of scope
- MPLAB-generated makefiles without the IDE: `prjMakefilesGenerator.sh`, `hexmate`, `fixDeps` and `mplab_platform` paths ([[task:b0aa04ab-d641-4239-9d2a-dc12f0d930ba][task b0aa04ab]]).
- Per-compiler pack sets ([[task:aebb7421-fa4a-4b4b-b536-97dbdf8ef1b4][task aebb7421]]).
- Pack dependency resolution.
- Changes to compiler payloads or to `xclm.conf` beyond the existing licence path patch.
- A compiler call from one environment into an unrelated environment (see `** Decisions`).
- CI runner set-up (unprivileged user namespaces in containers).

- [X] `xc-cli` with no override builds, and `xc-run true` exits 0.

- [ ] An `xc-cli` wrapper called inside its own environment (e.g. from a Makefile under `xc-make`) runs the compiler without a new bwrap call.
- [ ] An `xc-cli` wrapper called inside an `mplab-x` environment built from that `xc-cli` (e.g. from a Makefile under `mplab-make`) runs the compiler without a new bwrap call.
- [ ] A wrapper called inside an unrelated environment exits non-zero with a message that names both environments.
- [ ] `mplab_ide` removes `xc-cli` bin directories from `PATH` as it does for `mplab-x` bin directories.
*** Anti-criteria
- [X] Must not: modify compiler payloads.
- [X] Must not: add a mount to the environment (README.org: each block-device mount costs each compile an `xclm` search).
- [X] Must not: give `xc-cli` a build or run dependency on `mplab-x-unwrapped` (its version string only).
- [X] Must not: change the remaining default compiler versions in `pkgs/default.nix` (e.g. `xc16 = xc16_1_61`).

** Decisions
- `xc-cli` owns the compiler and pack selection, and `mplab-x` builds its root filesystem from the inputs of an `xc-cli` (user decision, 2026-10-21) :: one selection for the CLI and the IDE, no duplicate compiler wrappers on `PATH`, and an `xc-cli` wrapper can run directly inside an `mplab-x` environment that contains its compiler paths. The `xc-cli` closure has no IDE. The IDE-free follow-on (task b0aa04ab) adds an `mplab_platform` subset to `xc-cli`, and `mplab-x` gets it too.
  Rejected:
  - Separate `compilers` and `packs` arguments on both packages: two selections that can drift, two wrappers with one name in a devshell, and nested calls that fail between the two roots.
  - Layer the built `xc-cli` root filesystem under the IDE root at run time: `run.sh` merges one root filesystem with the host; a second layer adds merge logic for each call, and the separate `mplab-x` root costs mostly symlinks.
  - An `ide = false` argument of `mplab-x`: one package with two root filesystems, and the small closure only with an override.
- An eval-time assertion that the IDE version of `xc-cli` equals `mplab-x-unwrapped.version` :: both packs folders are at /opt/microchip/mplabx/v<version>/packs, so a mismatch puts the packs where the IDE does not look.
- The `mplab-x` `packs` argument adds IDE-only packs :: tool packs (e.g. ICD4_TP) are needed to program and debug, not to compile, so they stay out of the `xc-cli` closure.
  Rejected:
  - Tool packs in `xc-cli` only: one place to select packs, but a larger CLI closure.
- Packs at /opt/microchip/mplabx/v<version>/packs, with <version> from `mplab-x-unwrapped.version` :: the DFP_DIR path of MPLAB-generated makefiles (task 77c12e60). The version is a string, so `xc-cli` does not build or refer to the IDE.
  Rejected:
  - /opt/microchip/packs: differs from DFP_DIR, so task b0aa04ab would need a second path.
- No default compiler and no default packs in `xc-cli` and `mplab-x`; no `compilers` argument on `mplab-x`; `mplab-xc*` removed :: each installation states what it needs, and no closure gets a compiler or 14 GB of packs that it did not request (user decision, 2026-10-21).
  Rejected:
  - Keep `mplab-xc*` with a per-compiler pack set: a rule from the compiler subdirectory of each pack misses about 40 device packs (measured 2026-10-21); deferred to task aebb7421.
- A wrapper called inside an unrelated environment fails with a message :: a second bwrap call inside `mplab-x-run` fails with `bwrap: setting up uid map: Operation not permitted` (measured 2026-10-21), so it cannot enter its own root filesystem, and the compiler path that it expects can be absent there. The environment marker names the `xc-cli` that the root filesystem contains, so an `mplab-x` built from an `xc-cli` is not unrelated to it.
  Rejected:
  - Run the compiler from its store path when nested: the compiler then depends on the other root filesystem's libraries, without a test.

** Risks
- xc8, xc32 and xc-dsc can need libraries beyond glibc, libstdc++ and libgcc. Only xc16 1.61 and 1.21 were measured (`DT_NEEDED`: glibc, 32-bit libstdc++ and libgcc_s), and neither names /opt/microchip.
- The IDE with an empty packs folder is not tested; a GUI check is in the removal task.
- Downstream projects that use `mplab-xc16`, the `mplab-x` `compilers` argument or the `mplab-x` default compiler fail to evaluate or lose their compiler after the update. README.org gives the migration.
- A devshell with `mplab-x` and no `xc-cli` has no command-line compilers; README.org examples list both.

* Implementation
- `pkgs/mplab-x/rootfs.nix` takes the FHS package lists, compiler and pack selections, pack version, extra root filesystem and pack commands, and command names; it returns the root filesystem, run and make scripts, wrappers, and FHS package lists.
- `mplab-x` supplies its GUI and IDE root filesystem content as extra commands, so the generic builder can assemble a compiler-only root filesystem without an IDE input.
- `xc-cli` uses only glibc and `gcc.cc.lib` in a multi-architecture FHS root filesystem; the latter supplies 32-bit libstdc++ and libgcc_s for xc16 1.21 and sim30.
